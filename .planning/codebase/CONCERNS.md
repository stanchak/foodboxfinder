# Codebase Concerns

**Analysis Date:** 2026-03-20

## Tech Debt

**Stale Prisma generated client:**
- Issue: The generated Prisma client in `src/generated/prisma/` was generated before models were added to the schema. `src/generated/prisma/enums.ts` explicitly says "there are no enums in the schema" despite the schema defining 6 enums (`CategoryType`, `DietaryTag`, `PlanFrequency`, `ReviewStatus`, `ContentStatus`). The `src/generated/prisma/models.ts` only re-exports `commonInputTypes` with no actual model types.
- Files: `src/generated/prisma/enums.ts`, `src/generated/prisma/models.ts`, `src/generated/prisma/internal/class.ts`
- Impact: Any code importing Prisma types or using the client will fail at compile time. The `prisma` instance from `src/lib/db.ts` will have no model accessors (no `prisma.provider`, `prisma.plan`, etc.). All downstream development is blocked until this is fixed.
- Fix approach: Run `npx prisma generate` to regenerate the client from the current `prisma/schema.prisma`. The `build` script in `package.json` already includes `prisma generate && next build`, but a fresh generate is needed for development. Add a `postinstall` script: `"postinstall": "prisma generate"` to `package.json` so this happens automatically after `npm install`.

**Default create-next-app boilerplate remains:**
- Issue: `src/app/page.tsx` is the complete default Next.js create-next-app template with Vercel branding ("Deploy Now" button, links to Vercel templates and Next.js learning center, `next.svg` and `vercel.svg` images). `src/app/layout.tsx` exports metadata with `title: "Create Next App"` and `description: "Generated by create next app"`.
- Files: `src/app/page.tsx`, `src/app/layout.tsx`
- Impact: If deployed to Vercel (the `.vercel/` directory shows a deployment was already attempted), Google indexes placeholder metadata. Preview deployment URLs show misleading content and titles. Social share cards display "Create Next App" instead of FoodBoxFinder.
- Fix approach: Replace during Phase 20 (layout shell) and Phase 30 (homepage). Update `metadata` in `src/app/layout.tsx` to FoodBoxFinder branding as the very first task of Phase 20.

**No seed script:**
- Issue: `prisma/seed.ts` does not exist. The Phase 10 plan specifies a comprehensive seed script with 18 providers across 5 categories, but no seed data files exist. The `prisma/` directory contains only `schema.prisma`.
- Files: `prisma/seed.ts` (missing), `prisma/seed-data/` (missing directory)
- Impact: Blocks all UI development. Every phase from 20 onward depends on database content for development and visual testing. Without seed data, developers cannot verify that pages render correctly.
- Fix approach: Phase 10, Tasks 3-4 create the seed script and configure the `prisma.seed` command in `package.json`. Also add `tsx` to devDependencies for running the seed script.

**No database query utilities:**
- Issue: `src/lib/` contains only `db.ts` (Prisma client singleton). The ~20 query functions planned in Phase 10 Task 5 (e.g., `getFeaturedProviders`, `getProvidersByCategory`, `getProviderBySlug`, `searchProviders`) do not exist.
- Files: `src/lib/queries.ts` (missing)
- Impact: Every page that fetches data needs these functions. Without a shared query layer, duplicate query logic will proliferate across Server Components. All phases from 30 onward are blocked.
- Fix approach: Phase 10, Task 5 creates `src/lib/queries.ts`. Plan calls for a single file for MVP, to be split when it exceeds 300 lines into `src/lib/queries/providers.ts`, `src/lib/queries/content.ts`, `src/lib/queries/admin.ts`, `src/lib/queries/analytics.ts`.

**next.config.ts is empty:**
- Issue: `next.config.ts` contains a default empty `NextConfig` object with a placeholder comment. No `images.remotePatterns` (required for external provider logos/hero images via Next.js Image component), no `cacheComponents: true` (Next.js 16 caching), no project-specific settings.
- Files: `next.config.ts`
- Impact: External images from provider CDNs will throw errors with the Next.js Image component. No ISR or cache strategy is active. The `images.domains` config is deprecated in Next.js 16 -- only `images.remotePatterns` works.
- Fix approach: Add `images.remotePatterns` when implementing provider detail pages (Phase 50). Enable `cacheComponents: true` during Phase 110 (SEO & Performance).

**globals.css font override conflict:**
- Issue: `src/app/globals.css` line 26 sets `body { font-family: Arial, Helvetica, sans-serif; }` which overrides the Geist font loaded via `next/font/google` in `src/app/layout.tsx`. The layout correctly sets CSS variables (`--font-geist-sans`, `--font-geist-mono`) and maps them to `--font-sans`/`--font-mono` Tailwind theme tokens, but the hard-coded `body` rule takes precedence.
- Files: `src/app/globals.css` (line 26), `src/app/layout.tsx` (lines 5-13)
- Impact: Geist font files are downloaded (increasing page weight) but never visually applied. The site renders in Arial instead. Font inconsistency between design intent and actual rendering.
- Fix approach: Remove the `body { font-family: Arial, Helvetica, sans-serif; }` rule from `globals.css`. The Tailwind `--font-sans` variable (mapped to `--font-geist-sans`) will take effect through the `font-sans` utility class. Fix during Phase 20 (Design System).

**prosJson/consJson stored as text strings instead of JSON type:**
- Issue: `Provider.prosJson` and `Provider.consJson` are `String @db.Text` containing serialized JSON arrays. Prisma supports a `Json` type that maps to PostgreSQL JSONB, which provides database-level validation and queryability.
- Files: `prisma/schema.prisma` (lines 84-85)
- Impact: No database-level validation of JSON structure. Every consumer must `JSON.parse()` and handle parse errors. Cannot query or filter within pros/cons at the database level. No type safety -- the field could contain any string.
- Fix approach: Change to `Json?` type before seeding data in Phase 10 to avoid a data migration. Alternatively, accept the tech debt for MVP and create typed helper functions: `parsePros(provider): string[]` and `parseCons(provider): string[]` with error handling.

**Float type for monetary values:**
- Issue: All pricing fields use `Float`: `Plan.pricePerServing`, `Plan.pricePerWeek`, `Plan.pricePerBox`, `Plan.shippingCost`, and the denormalized `Provider.minPricePerServing`/`Provider.maxPricePerServing` (planned in Phase 10 Task 1). IEEE 754 floating-point arithmetic causes rounding errors with decimal values (`0.1 + 0.2 !== 0.3`).
- Files: `prisma/schema.prisma` (lines 121-124, Plan model)
- Impact: Price comparisons may produce incorrect results. Display values may show artifacts like `$4.990000000000001`. Sorting by price could produce unexpected ordering.
- Fix approach: Change pricing fields to `Decimal` type (Prisma maps to PostgreSQL `DECIMAL`/`NUMERIC`) or store as integer cents (`pricePerServingCents Int?`). Make this change before seeding data in Phase 10. The `averageRating Float` field is acceptable since ratings are inherently approximate.

## Security Considerations

**No admin authentication mechanism:**
- Risk: Project plan (AD-4 in `.planning/PROJECT.md`) specifies admin protection via `proxy.ts` using an `ADMIN_SECRET` environment variable or basic auth. No `proxy.ts` file exists at any location. In Next.js 16, this file replaces `middleware.ts` and must export a `proxy` function (not `middleware`), running in Node.js runtime only.
- Files: `proxy.ts` (missing at project root and all other locations checked)
- Current mitigation: No admin routes exist yet, so nothing is exposed.
- Recommendations: Create `proxy.ts` at the project root as the absolute first step of Phase 100 (Admin Dashboard), before creating any admin routes or pages. Test that unauthenticated requests to `/admin/*` are rejected before building any admin UI.

**DATABASE_URL used with non-null assertion:**
- Risk: `src/lib/db.ts` line 11 uses `process.env.DATABASE_URL!`. If `DATABASE_URL` is not set, `undefined` is passed to PrismaPg adapter, producing a cryptic connection error rather than a clear failure message.
- Files: `src/lib/db.ts` (line 11)
- Current mitigation: `.env` file exists locally with the value set.
- Recommendations: Add a runtime guard before the Prisma client construction:
  ```typescript
  const databaseUrl = process.env.DATABASE_URL;
  if (!databaseUrl) throw new Error("DATABASE_URL environment variable is required");
  ```

**No .env.example file:**
- Risk: New developers or CI systems have no reference for required environment variables. `.env` is correctly gitignored (`.gitignore` line 34: `.env*`), but no template exists.
- Files: `.env.example` (missing)
- Current mitigation: None. Required variables must be discovered by reading source code.
- Recommendations: Create `.env.example` with documented placeholder values. Currently required: `DATABASE_URL=postgresql://user:password@host/database`. Future: `ADMIN_SECRET=change-me-in-production`.

**Review model stores authorEmail in plaintext:**
- Risk: `Review.authorEmail` (`String?`) stored without hashing or encryption. Database compromise exposes all reviewer email addresses. GDPR and privacy compliance may require protections.
- Files: `prisma/schema.prisma` (line 166)
- Current mitigation: Field is optional.
- Recommendations: For MVP, document that email is used only for dedup/spam prevention and is never displayed publicly. Consider hashing email for dedup comparisons in a future phase. Include privacy policy text on the review form.

**No rate limiting infrastructure:**
- Risk: Review submission (Phase 90) and affiliate click tracking (Phase 120) have no rate limiting. Phase 90 acceptance criteria mention "basic rate limiting" but no infrastructure exists.
- Files: No rate limiting code exists; no rate limiting library in `package.json`
- Current mitigation: Reviews default to `PENDING` status, providing admin moderation as a safety net.
- Recommendations: Implement IP-based rate limiting on Server Actions. Options: check recent submissions from the same IP hash (similar to `AffiliateClick.ipHash` pattern), add a honeypot field, or integrate a lightweight library. Consider adding CAPTCHA for the review form.

**No input validation library:**
- Risk: No validation library (zod, yup, valibot) in `package.json`. All user inputs (review submissions, admin forms, search queries) need validation against XSS and data integrity issues.
- Files: `package.json` (no validation dependency)
- Current mitigation: Prisma provides parameterized queries preventing SQL injection.
- Recommendations: Add `zod` as a dependency. Define validation schemas for all user-facing Server Actions (review submission, admin provider CRUD, blog post creation). Validate on both client and server.

## Performance Bottlenecks

**No caching strategy configured:**
- Problem: `next.config.ts` does not enable `cacheComponents: true` (Next.js 16 caching feature). Provider listings and detail pages are read-heavy with infrequent updates -- ideal for caching.
- Files: `next.config.ts`
- Cause: Default scaffold state. Caching planned for Phase 110.
- Improvement path: Enable `cacheComponents: true` in `next.config.ts`. Apply `use cache` directive and `cacheLife()` to data-heavy Server Components. Add `export const revalidate` to listing pages for ISR.

**Denormalized fields have no sync mechanism:**
- Problem: `Provider.averageRating`, `Provider.reviewCount` (and the planned `minPricePerServing`, `maxPricePerServing`, `freeShipping`) are denormalized for listing performance but have no automated sync when underlying data (reviews, plans) changes.
- Files: `prisma/schema.prisma` (lines 79-81)
- Cause: Intentional denormalization. Sync logic deferred to Phase 90 (reviews) and Phase 100 (admin plan management).
- Improvement path: Create utility functions like `recalculateProviderRating(providerId)` and `recalculateProviderPricing(providerId)`. Call these in every Server Action that modifies reviews or plans. Consider wrapping in a Prisma middleware for automatic sync.

**No full-text search indexes:**
- Problem: Phase 80 (Search) requires PostgreSQL full-text search, but no `tsvector` columns or GIN indexes exist in the schema.
- Files: `prisma/schema.prisma`
- Cause: Deferred to Phase 80 by design. Phase 10 plan uses `contains` as a stopgap for MVP search.
- Improvement path: Add `tsvector` generated columns and GIN indexes to `Provider`, `BlogPost`, and `Collection` when implementing Phase 80. This requires raw SQL via `prisma db execute` since Prisma does not natively support `tsvector`.

**AffiliateClick table has unbounded growth:**
- Problem: Every affiliate click creates a new row with no retention policy, archival, or cleanup.
- Files: `prisma/schema.prisma` (lines 262-276)
- Cause: No analytics data lifecycle management designed.
- Improvement path: Implement periodic aggregation (e.g., roll up daily click counts per provider) and delete raw rows older than 90 days. The `@@index([createdAt])` on the model supports efficient time-range queries for cleanup.

## Fragile Areas

**Prisma client singleton pattern:**
- Files: `src/lib/db.ts`
- Why fragile: Uses `globalThis` type casting (`globalThis as unknown as { prisma: PrismaClient | undefined }`) for development hot-reload singleton. This is the standard Next.js/Prisma pattern but silently creates multiple connections in production if the guard is wrong, or if used in an Edge runtime (Prisma does not support Edge).
- Safe modification: Never create `new PrismaClient()` outside this file. Always import from `@/lib/db`. Do not change the `NODE_ENV !== "production"` guard condition.
- Test coverage: None.

**Schema changes require manual multi-step process:**
- Files: `prisma/schema.prisma`, `src/generated/prisma/`
- Why fragile: After any schema change, developers must run both `npx prisma db push` (sync to Neon) and `npx prisma generate` (update TypeScript types). Forgetting either step causes type errors (stale generated client) or runtime errors (schema mismatch). The `build` script includes `prisma generate` but the `dev` script does not. The generated client is gitignored (`/src/generated/prisma` in `.gitignore` line 43), so every fresh clone must generate it.
- Safe modification: Always run `npx prisma db push && npx prisma generate` after schema changes. Add `"postinstall": "prisma generate"` to `package.json` to automate on `npm install`. Consider adding `prisma generate` to the `dev` script.
- Test coverage: None.

**Next.js 16 breaking changes affect every future page:**
- Files: `AGENTS.md`, all future `src/app/` files
- Why fragile: Next.js 16 introduces several breaking changes that will affect every dynamic route. Developers (and AI assistants) trained on Next.js 14/15 patterns will write broken code:
  1. `params` and `searchParams` are Promises -- must `await` in every page/layout/route handler.
  2. `proxy.ts` replaces `middleware.ts` -- different export name and Node.js runtime only.
  3. `cookies()`, `headers()`, `draftMode()` are async -- must `await`.
  4. `useFormState` renamed to `useActionState` (React 19).
  5. Parallel route slots require explicit `default.js` -- builds fail without them.
- Safe modification: Follow `AGENTS.md` strictly. Consult `node_modules/next/dist/docs/01-app/` for current API docs. Always `await params` and `await searchParams` in pages.
- Test coverage: None.

**Single-category enum on Provider:**
- Files: `prisma/schema.prisma` (line 100)
- Why fragile: Each `Provider` has exactly one `CategoryType`. If a provider spans categories (e.g., a meal kit service that also offers prepared meals), the schema cannot represent this. Changing from a single enum to a many-to-many relation after data is seeded requires a data migration.
- Safe modification: Evaluate during Phase 10 seed data creation whether any providers span categories. If so, consider a junction table (`ProviderCategory`) similar to `ProviderDietaryTag` before seeding.
- Test coverage: None.

**JSON string fields with no validation:**
- Files: `prisma/schema.prisma` (lines 84-85)
- Why fragile: `Provider.prosJson` and `Provider.consJson` are `String @db.Text` containing JSON arrays. Any code path that writes these fields could store malformed JSON, causing `JSON.parse()` to throw at runtime on every subsequent read.
- Safe modification: Create typed helper functions with error handling: `parsePros(json: string | null): string[]` and `parseCons(json: string | null): string[]`. Use these everywhere instead of raw `JSON.parse()`. Validate JSON before writing.
- Test coverage: None.

## Scaling Limits

**Single-file query architecture:**
- Current capacity: Phase 10 plans ~20 query functions in a single `src/lib/queries.ts`.
- Limit: File will exceed 300 lines as admin queries, analytics queries, and search queries are added. Becomes difficult to navigate and maintain.
- Scaling path: Phase 10 plan acknowledges this: "split later when any file > 300 lines." Suggested split: `src/lib/queries/providers.ts`, `src/lib/queries/content.ts`, `src/lib/queries/admin.ts`, `src/lib/queries/analytics.ts` with a barrel export at `src/lib/queries/index.ts`.

**Neon serverless connection limits:**
- Current capacity: Neon free tier provides 100 concurrent connections via pooling.
- Limit: Under high traffic with Vercel serverless functions, each function invocation establishes a connection. Connection pool exhaustion causes 500 errors.
- Scaling path: Ensure `DATABASE_URL` uses Neon's pooled connection URL (port 6543). Monitor in Neon dashboard. Upgrade tier if needed. The `@prisma/adapter-pg` with `PrismaPg` already uses optimized serverless connections.

**AffiliateClick unbounded growth:**
- Current capacity: No limits on row count or retention.
- Limit: Over months/years, this table grows indefinitely. Queries for analytics become slower. Storage costs increase.
- Scaling path: Add periodic aggregation (monthly click counts per provider) and prune raw rows older than 90 days. The `@@index([createdAt])` supports efficient time-range deletes.

## Dependencies at Risk

**Next.js 16 community maturity:**
- Risk: Next.js 16 is very new. Community resources, Stack Overflow answers, tutorials, and third-party library compatibility may lag behind. AI code assistants may generate Next.js 14/15 patterns from training data.
- Impact: Developers may write code using deprecated APIs (`middleware.ts`, synchronous `params`, `images.domains`, `useFormState`) that compiles but fails at runtime.
- Migration plan: Always consult `node_modules/next/dist/docs/` and `AGENTS.md` for current patterns. Test all pages at runtime, not just compile time.

**No component library:**
- Risk: All UI components (Button, Card, Badge, Input, Select, Rating stars, Modal, Accordion, Dropdown) built from scratch. Accessibility (ARIA attributes, keyboard navigation, focus management) must be manually implemented.
- Impact: Phase 20 requires significant effort for the design system. Complex interactive components (modals, dropdowns, accordions in Phase 50 FAQ) are error-prone to build accessibly.
- Migration plan: Consider adding Radix UI or Headless UI for complex interactive components to get accessibility for free. Keep simple components (Button, Card, Badge) custom with Tailwind.

**No markdown rendering library:**
- Risk: Phase 70 (Blog) requires markdown/rich text rendering for blog post bodies. No markdown library (remark, rehype, next-mdx-remote) is in dependencies.
- Impact: Blog implementation blocked until a markdown strategy is chosen and library installed.
- Migration plan: Add `remark` + `rehype` packages (or `next-mdx-remote` for MDX) when implementing Phase 70.

**Prisma 7.5 with pg adapter:**
- Risk: Prisma 7 with `@prisma/adapter-pg` bypasses Prisma's query engine for direct PostgreSQL driver queries. Some Prisma features may behave differently or have edge cases with this adapter.
- Impact: Full-text search (Phase 80), aggregations (rating calculations), and complex filtered queries need verification with the pg adapter specifically.
- Migration plan: Monitor Prisma release notes. If issues arise, fall back to the standard Prisma engine by removing the adapter config and using `DATABASE_URL` directly in the datasource block.

**No favicon or branding assets:**

## Test Coverage Gaps

**Zero test infrastructure:**
- What's not tested: Everything. No test framework installed (no jest, vitest, playwright, cypress in `package.json`). No test config files. No test files anywhere in the project.
- Files: `package.json` (no test dependencies), no `*.test.*` or `*.spec.*` files
- Risk: All future code has no regression safety net. The most critical untested areas as the project grows will be:
  - Database query functions (data integrity, filter logic)
  - Server Actions for review submission (validation, rate limiting)
  - Admin authentication (security)
  - Rating/pricing recalculation (data consistency)
  - Price comparison logic (financial accuracy)
  - URL filter/sort state parsing (user-facing correctness)
- Priority: High. Install Vitest (lightweight, good Next.js integration) during Phase 10. Write unit tests for every query utility. Add integration tests for Server Actions in Phase 90/100. Add E2E tests (Playwright) before launch.

**No CI/CD pipeline:**
- What's not tested: Automated type checking, linting, and test execution on pull requests.
- Files: No `.github/workflows/` directory, no CI configuration
- Risk: Type errors, lint violations, and regressions can be merged without detection. The project relies entirely on developer discipline.
- Priority: Medium. Add a GitHub Actions workflow running `npx eslint .`, `npx tsc --noEmit`, and `npx vitest run` (once tests exist) on pull requests. The Vercel integration provides build verification but not type checking or testing.
