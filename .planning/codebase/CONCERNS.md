# Codebase Concerns

**Analysis Date:** 2026-03-20

## Tech Debt

**Stale Prisma generated client:**
- Issue: The generated client in `src/generated/prisma/` was generated before models were added to the schema. `src/generated/prisma/enums.ts` says "there are no enums in the schema" despite the schema defining 6 enums. `src/generated/prisma/models.ts` only re-exports `commonInputTypes` with no actual model types. The `prisma` singleton from `src/lib/db.ts` has no model accessors (`prisma.provider`, `prisma.plan`, etc.).
- Files: `src/generated/prisma/enums.ts`, `src/generated/prisma/models.ts`, `src/generated/prisma/internal/class.ts`, `src/lib/db.ts`
- Impact: All code importing Prisma types or using model accessors will fail at compile time. Every downstream phase is blocked until this is fixed.
- Fix approach: Run `npx prisma generate` to regenerate from `prisma/schema.prisma`. Add `"postinstall": "prisma generate"` to `package.json` so fresh clones auto-generate. The `build` script already runs `prisma generate && next build`, but development requires a manual generate after clone.

**Default create-next-app boilerplate remains:**
- Issue: `src/app/page.tsx` is the complete Next.js scaffold template with Vercel branding ("Deploy Now" button, Next.js learning links, `next.svg`/`vercel.svg` images). `src/app/layout.tsx` has `title: "Create Next App"` and `description: "Generated by create next app"` in metadata.
- Files: `src/app/page.tsx`, `src/app/layout.tsx`
- Impact: The `.vercel/` directory shows a deployment was already attempted. If indexed, Google sees "Create Next App" instead of FoodBoxFinder. Social share cards display wrong branding.
- Fix approach: Replace homepage in Phase 30 and update `metadata` in `src/app/layout.tsx` as the first task of Phase 20.

**No seed script or query layer:**
- Issue: `prisma/seed.ts` does not exist. No `prisma/seed-data/` directory. `src/lib/queries.ts` does not exist. The only source file in `src/lib/` is `db.ts` (the Prisma singleton).
- Files: `prisma/seed.ts` (missing), `prisma/seed-data/` (missing), `src/lib/queries.ts` (missing)
- Impact: Blocks all UI development. Every phase from 20 onward needs database content and query functions. Without seed data, pages cannot be visually tested or verified.
- Fix approach: Phase 10 Tasks 3-5 create the seed script, seed data files, and query utilities.

**next.config.ts is empty:**
- Issue: Contains a default empty `NextConfig` object. No `images.remotePatterns` (required for external provider images), no `cacheComponents: true` (Next.js 16 caching), no project-specific settings.
- Files: `next.config.ts`
- Impact: External images from provider CDNs will throw `next/image Un-configured Host` errors. No ISR or caching active. `images.domains` is deprecated in Next.js 16.
- Fix approach: Add `images.remotePatterns` when seed data URLs are known (Phase 10). Enable `cacheComponents: true` during Phase 110.

**globals.css font override conflict:**
- Issue: `src/app/globals.css` line 25 sets `body { font-family: Arial, Helvetica, sans-serif; }` which overrides the Geist font loaded via `next/font/google` in `src/app/layout.tsx`. The layout sets CSS variables `--font-geist-sans` and maps them to Tailwind's `--font-sans` theme token at line 11, but the hard-coded body rule takes precedence.
- Files: `src/app/globals.css` (line 25), `src/app/layout.tsx` (lines 5-13)
- Impact: Geist font files are downloaded (wasted bytes) but never rendered. The site displays in Arial instead of the intended font.
- Fix approach: Remove the `body { font-family: Arial, Helvetica, sans-serif; }` rule from `globals.css`. Tailwind's `--font-sans` variable (mapped to Geist) will apply automatically. Fix during Phase 20.

**Float type for all monetary values:**
- Issue: All pricing fields use `Float`: `Plan.pricePerServing`, `Plan.pricePerWeek`, `Plan.pricePerBox`, `Plan.shippingCost`. IEEE 754 floating-point arithmetic causes `0.1 + 0.2 = 0.30000000000000004`.
- Files: `prisma/schema.prisma` (lines 121-124, Plan model)
- Impact: Price displays may show `$4.990000000000001`. Price sorting produces incorrect ordering when values differ by fractions of a cent. Price filter boundaries behave unpredictably (a `$8.00` item stored as `$8.000000000001` excluded from `<= $8.00` filter). This is a data integrity problem, not just a display issue.
- Fix approach: Change pricing fields to `Decimal` (maps to PostgreSQL `DECIMAL`/`NUMERIC`) or store as integer cents (`pricePerServingCents Int?`) before seeding any data in Phase 10. `averageRating Float` is acceptable since ratings are inherently approximate.

**prosJson/consJson stored as Text instead of JSON type:**
- Issue: `Provider.prosJson` and `Provider.consJson` are `String @db.Text` containing serialized JSON arrays. Prisma supports a `Json` type mapping to PostgreSQL JSONB with database-level validation.
- Files: `prisma/schema.prisma` (lines 84-85)
- Impact: No database-level validation of JSON structure. Any malformed write causes `JSON.parse()` to throw on every subsequent read of that provider. Since these render on listing and detail pages, one corrupt record crashes page rendering for that provider.
- Fix approach: Change to `Json?` type before seeding data in Phase 10. Alternatively, create typed helper functions `parsePros(json: string | null): string[]` and `parseCons(json: string | null): string[]` with try/catch returning `[]` on failure.

**Single-category enum limits Provider modeling:**
- Issue: Each Provider has exactly one `CategoryType` enum value. Real-world providers span multiple categories: Hungryroot is both meal kit and grocery, Sunbasket offers meal kits and prepared meals, Green Chef is both meal kit and specialty.
- Files: `prisma/schema.prisma` (line 100)
- Impact: Providers appear in the wrong category or are missing from categories where users expect them. Category page provider counts are inaccurate. Changing to a junction table after seeding requires a data migration.
- Fix approach: Evaluate during Phase 10 seed data creation. If 3+ of the 18 planned providers span categories, convert to a `ProviderCategory` junction table following the `ProviderDietaryTag` pattern already in the schema. At minimum, add `secondaryCategory CategoryType?`.

## Known Bugs

No runtime bugs exist at this stage. The project is in initial scaffolding state with only 3 hand-written source files. However, two issues will manifest as bugs as soon as development begins:

**Prisma client has no model accessors:**
- Symptoms: `Property 'provider' does not exist on type 'PrismaClient'` at compile time. Any query like `prisma.provider.findMany()` fails.
- Files: `src/generated/prisma/internal/class.ts`, `src/lib/db.ts`
- Trigger: Import `prisma` from `@/lib/db` and attempt any model operation.
- Workaround: Run `npx prisma generate` to regenerate the client.

**Dark mode colors defined but project scopes dark mode out:**
- Symptoms: `globals.css` defines dark mode colors (`--background: #0a0a0a`, `--foreground: #ededed` in `prefers-color-scheme: dark` media query) and `page.tsx` uses `dark:` Tailwind variants throughout. PROJECT.md explicitly says "Dark mode -- deprioritized for launch."
- Files: `src/app/globals.css` (lines 15-20), `src/app/page.tsx` (multiple `dark:` classes)
- Trigger: Users with OS dark mode enabled see dark theme on the boilerplate page.
- Workaround: Remove `dark:` variants and dark color definitions when replacing boilerplate in Phase 20. No active harm since the boilerplate page is replaced entirely.

## Security Considerations

**No admin authentication mechanism:**
- Risk: The project requires admin protection via `proxy.ts` using `ADMIN_SECRET` env var. No `proxy.ts` file exists anywhere. In Next.js 16, this file replaces `middleware.ts` and must export a `proxy` function (not `middleware`), running in Node.js runtime only (not Edge).
- Files: `proxy.ts` (missing at project root)
- Current mitigation: No admin routes exist yet, so nothing is exposed.
- Recommendations: Create `proxy.ts` as the absolute first step of Phase 100, before creating any admin routes. Test that unauthenticated requests to `/admin/*` are rejected before building any admin UI.

**DATABASE_URL accessed with non-null assertion:**
- Risk: `src/lib/db.ts` line 11 uses `process.env.DATABASE_URL!`. If the variable is unset, `undefined` is passed to the PrismaPg adapter, producing a cryptic connection error instead of a clear failure message.
- Files: `src/lib/db.ts` (line 11)
- Current mitigation: `.env` file exists locally with the value set.
- Recommendations: Add a runtime guard: `if (!process.env.DATABASE_URL) throw new Error("DATABASE_URL environment variable is required")`. Better: install `zod` and create `src/lib/env.ts` for centralized env validation.

**No .env.example file:**
- Risk: New developers and CI systems have no reference for required environment variables. `.env` is correctly gitignored, but no template exists.
- Files: `.env.example` (missing)
- Current mitigation: None. Required variables must be discovered by reading source code.
- Recommendations: Create `.env.example` with documented placeholders: `DATABASE_URL=postgresql://user:password@host/database` and `ADMIN_SECRET=change-me-in-production`.

**Review model stores authorEmail in plaintext:**
- Risk: `Review.authorEmail` (`String?`) stored without hashing. Database compromise exposes reviewer email addresses. GDPR compliance may require protections.
- Files: `prisma/schema.prisma` (line 166)
- Current mitigation: Field is optional.
- Recommendations: For MVP, document that email is for dedup/spam prevention only and never displayed. Consider hashing for dedup comparisons. Include privacy notice on the review form.

**No input validation library:**
- Risk: No validation library (`zod`, `yup`, `valibot`) in `package.json`. All user inputs (review submissions, admin forms, search queries) need validation for XSS and data integrity.
- Files: `package.json` (no validation dependency)
- Current mitigation: Prisma provides parameterized queries preventing SQL injection.
- Recommendations: Add `zod` as a dependency. Define validation schemas for all Server Actions. Validate on both client and server.

**No rate limiting infrastructure:**
- Risk: Review submission (Phase 90) and affiliate click tracking (Phase 120) have no rate limiting. No rate limiting library exists in dependencies.
- Files: `package.json` (no rate limiting dependency)
- Current mitigation: Reviews default to `PENDING` status, providing moderation as a safety net. But a spam flood makes the moderation queue unusable.
- Recommendations: Implement IP-hash-based rate limiting on Server Actions. Add honeypot fields to forms. Set minimum review body length and time-based submission checks.

**FTC affiliate disclosure not planned in component architecture:**
- Risk: FTC requires clear disclosure of affiliate relationships near affiliate links. Penalties up to $51,744 per violation in 2026. No `<AffiliateDisclosure />` component is planned in the design system.
- Files: No component exists; no architectural provision in `src/components/`
- Current mitigation: No affiliate links exist yet.
- Recommendations: Create a reusable `<AffiliateDisclosure />` component in Phase 20 that renders on every page with affiliate links. Create a `/disclosure` page linked from the site footer. Verify every page rendering `affiliateUrl` also renders disclosure.

## Performance Bottlenecks

**No caching strategy configured:**
- Problem: `next.config.ts` does not enable `cacheComponents: true`. Provider listings and detail pages are read-heavy with infrequent updates -- ideal candidates for caching.
- Files: `next.config.ts`
- Cause: Default scaffold state. Caching is planned for Phase 110.
- Improvement path: Enable `cacheComponents: true` in `next.config.ts`. Apply `use cache` directive and `cacheLife()` to data-heavy Server Components. Add `export const revalidate` to listing pages for ISR. Implement on-demand revalidation from admin actions.

**Denormalized fields have no sync mechanism:**
- Problem: `Provider.averageRating`, `Provider.reviewCount` (and the planned `minPricePerServing`, `maxPricePerServing`, `freeShipping`) are denormalized for listing performance but have no automated recalculation when underlying data changes.
- Files: `prisma/schema.prisma` (lines 79-81)
- Cause: Intentional denormalization. Sync logic deferred to Phase 90 (reviews) and Phase 100 (admin plan management).
- Improvement path: Create utility functions `recalculateProviderRating(providerId)` and `recalculateProviderPricing(providerId)`. Call these in every Server Action that modifies reviews or plans.

**No full-text search indexes:**
- Problem: Phase 80 requires PostgreSQL full-text search. No `tsvector` columns or GIN indexes exist.
- Files: `prisma/schema.prisma`
- Cause: Deferred to Phase 80. Phase 10 uses `contains` as a stopgap.
- Improvement path: Add `tsvector` generated columns and GIN indexes to `Provider`, `BlogPost`, and `Collection` via raw SQL in Phase 80. Prisma does not natively support `tsvector`.

**AffiliateClick table has unbounded growth:**
- Problem: Every affiliate click creates a new row with no retention policy, archival, or cleanup mechanism.
- Files: `prisma/schema.prisma` (lines 262-276)
- Cause: No analytics data lifecycle management designed.
- Improvement path: Implement periodic aggregation (roll up daily click counts per provider). Delete raw rows older than 90 days. The `@@index([createdAt])` supports efficient time-range deletes.

**Neon serverless connection pool exhaustion risk:**
- Problem: Each Vercel serverless function cold start creates a new database connection. Under moderate traffic (50+ concurrent requests), the Neon free tier's pooling limit can be exhausted.
- Files: `src/lib/db.ts`, `.env` (DATABASE_URL configuration)
- Cause: Serverless architecture multiplies connection count. If `DATABASE_URL` uses the direct connection (port 5432) instead of the pooled connection (port 6543), each function holds an exclusive connection.
- Improvement path: Verify `DATABASE_URL` uses Neon's pooled endpoint (port 6543). Add `?connection_limit=5` to the connection string. Enable ISR/caching to reduce database hits per request.

## Fragile Areas

**Prisma client singleton pattern:**
- Files: `src/lib/db.ts`
- Why fragile: Uses `globalThis` type casting (`globalThis as unknown as { prisma: PrismaClient | undefined }`) for development hot-reload singleton. Silently creates multiple connections if the guard is wrong or if used in Edge runtime (Prisma does not support Edge).
- Safe modification: Never create `new PrismaClient()` outside this file. Always import from `@/lib/db`. Do not change the `NODE_ENV !== "production"` guard.
- Test coverage: None.

**Schema changes require manual multi-step process:**
- Files: `prisma/schema.prisma`, `src/generated/prisma/`
- Why fragile: After any schema change, developers must run both `npx prisma db push` (sync to Neon) and `npx prisma generate` (update TypeScript types). Forgetting either causes type errors or runtime schema mismatches. The `build` script includes `prisma generate` but the `dev` script does not. The generated client is gitignored, so every fresh clone must generate it.
- Safe modification: Always run `npx prisma db push && npx prisma generate` after schema changes. Add `"postinstall": "prisma generate"` to `package.json`.
- Test coverage: None.

**Next.js 16 breaking changes affect every future page:**
- Files: All future `src/app/` files, `AGENTS.md`
- Why fragile: Next.js 16 introduces breaking changes that affect every dynamic route:
  1. `params` and `searchParams` are Promises -- must `await` in every page/layout/route handler
  2. `proxy.ts` replaces `middleware.ts` -- different export name, Node.js runtime only
  3. `cookies()`, `headers()`, `draftMode()` are async -- must `await`
  4. `useFormState` renamed to `useActionState` (React 19)
  5. Parallel route slots require explicit `default.js`
- Safe modification: Follow `AGENTS.md` strictly. Consult `node_modules/next/dist/docs/01-app/` for current APIs. Always `await params` and `await searchParams`.
- Test coverage: None.

**JSON string fields with no validation:**
- Files: `prisma/schema.prisma` (lines 84-85)
- Why fragile: `Provider.prosJson` and `Provider.consJson` are `String @db.Text`. Any code path that writes malformed JSON crashes every subsequent read. Admin form free-text entry is especially error-prone.
- Safe modification: Create typed helpers with error handling. Validate JSON before writing. Use list-based admin UI rather than raw JSON textarea.
- Test coverage: None.

**Single-category enum on Provider:**
- Files: `prisma/schema.prisma` (line 100)
- Why fragile: Changing from enum to junction table after data is seeded requires a data migration with downtime. The decision must be made in Phase 10 before seeding.
- Safe modification: If staying with enum, document which category each multi-category provider is assigned to and why. If switching to junction table, follow the `ProviderDietaryTag` pattern.
- Test coverage: None.

## Scaling Limits

**Single-file query architecture:**
- Current capacity: Phase 10 plans ~20 functions in `src/lib/queries.ts`.
- Limit: File exceeds 300 lines as admin, analytics, and search queries accumulate. Becomes difficult to navigate and maintain.
- Scaling path: Split into `src/lib/queries/providers.ts`, `src/lib/queries/content.ts`, `src/lib/queries/admin.ts`, `src/lib/queries/analytics.ts` with barrel export at `src/lib/queries/index.ts`.

**Neon serverless connection limits:**
- Current capacity: Neon free tier provides 100 concurrent connections via pooling.
- Limit: Under high traffic with Vercel serverless functions, each cold start creates a connection. Pool exhaustion causes 500 errors.
- Scaling path: Use Neon pooled endpoint (port 6543). Set `connection_limit=5` per function. Enable ISR/caching to reduce DB queries. Upgrade Neon tier if needed.

**AffiliateClick unbounded growth:**
- Current capacity: No limits on row count or retention.
- Limit: Over months, the table grows indefinitely. Analytics queries slow down. Storage costs increase.
- Scaling path: Aggregate monthly click counts per provider into a summary. Prune raw rows older than 90 days. Add `totalClickCount Int` to Provider for historical totals.

## Dependencies at Risk

**Next.js 16 community maturity:**
- Risk: Next.js 16 is very new. Community resources, tutorials, and third-party library compatibility may lag. AI assistants trained on 14/15 patterns generate deprecated code.
- Impact: Developers write `middleware.ts` instead of `proxy.ts`, use synchronous `params`, call `useFormState` instead of `useActionState`. Code compiles but fails at runtime.
- Migration plan: Always consult `node_modules/next/dist/docs/` and `AGENTS.md`. Test pages at runtime, not just compile time.

**No component library for accessible interactive elements:**
- Risk: All UI components built from scratch. Accessibility (ARIA, keyboard nav, focus management) must be manually implemented for modals, dropdowns, accordions.
- Impact: Phase 20 requires significant design system effort. Complex interactive components (FAQ accordion in Phase 50, comparison tray in Phase 60, admin forms in Phase 100) are error-prone to build accessibly.
- Migration plan: Consider adding Radix UI or Headless UI for complex interactive components. Keep simple components (Button, Card, Badge) custom with Tailwind.

**No markdown rendering library:**
- Risk: Phase 70 (Blog) requires markdown rendering for blog post bodies. No markdown library in dependencies.
- Impact: Blog implementation blocked until library is chosen and installed.
- Migration plan: Add `remark` + `rehype` packages or `next-mdx-remote` when implementing Phase 70.

**Prisma 7.5 with pg adapter bypasses query engine:**
- Risk: `@prisma/adapter-pg` uses direct PostgreSQL driver queries, bypassing Prisma's query engine. Some features may behave differently or have edge cases.
- Impact: Full-text search (Phase 80), aggregations, and complex filtered queries need verification specifically with the pg adapter.
- Migration plan: Monitor Prisma release notes. If issues arise, fall back to the standard engine by removing the adapter and using `DATABASE_URL` directly in the datasource.

## Test Coverage Gaps

**Zero test infrastructure:**
- What's not tested: Everything. No test framework installed (no jest, vitest, playwright, cypress). No test config. No test files.
- Files: `package.json` (no test dependencies)
- Risk: All future code has no regression safety net. The most critical untested areas as the project grows:
  - Database query functions (data integrity, filter logic, boundary conditions)
  - Server Actions for review submission (validation, rate limiting, XSS prevention)
  - Admin authentication via `proxy.ts` (security bypass)
  - Rating/pricing recalculation (data consistency)
  - Price comparison and sorting (financial accuracy, Float arithmetic)
  - URL filter/sort state parsing (edge cases, malformed input)
  - Affiliate click tracking (dedup, attribution accuracy)
- Priority: High. Install Vitest during Phase 10. Write unit tests for every query utility. Add integration tests for Server Actions in Phase 90/100. Add E2E tests (Playwright) before launch in Phase 120.

**No CI/CD pipeline:**
- What's not tested: Automated type checking, linting, and test execution on pull requests.
- Files: No `.github/workflows/` directory
- Risk: Type errors, lint violations, and regressions can be merged without detection. The project relies entirely on developer discipline. Vercel provides build verification but not type checking or testing.
- Priority: Medium. Add GitHub Actions running `npx eslint .`, `npx tsc --noEmit`, and `npx vitest run` on pull requests.
